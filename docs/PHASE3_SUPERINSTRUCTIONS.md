# Phase 3: Superinstructions

## Overview

Phase 3 implements superinstructions—fused opcodes that combine frequently occurring instruction pairs into single opcodes. This optimization provides both bytecode size reduction and runtime performance improvement by reducing dispatch overhead.

## Motivation

Based on bytecode analysis from Phase 1, we identified several frequently occurring instruction patterns:

1. **DEFINE_GLOBAL + CONSTANT** - Variable initialization with constant values
2. **GET_GLOBAL + ADD** - Global variable arithmetic operations
3. **GET_GLOBAL + GET_GLOBAL** - Loading two globals (common in binary operations)
4. **GET_LOCAL + GET_LOCAL** - Loading two locals (common in binary operations)
5. **CONSTANT + CONSTANT** - Loading two constants sequentially

These patterns occur frequently enough to justify dedicated superinstructions.

## Benefits

### Bytecode Size Reduction
- Each fused instruction saves 1-2 bytes by eliminating one opcode
- Expected reduction: 3-5% on typical code

### Runtime Performance Improvement
- Reduces VM dispatch overhead (one dispatch instead of two)
- Reduces instruction fetch operations
- Improves instruction cache locality
- Expected speedup: 5-10% on instruction-heavy workloads

## Implementation Strategy

### 1. Opcode Allocation
Superinstructions use opcodes 100-191 (92 opcodes available):

```
100-109: DEFINE/SET patterns (10 opcodes)
110-119: GET + arithmetic patterns (10 opcodes)
120-129: GET + GET patterns (10 opcodes)
130-139: CONSTANT + operation patterns (10 opcodes)
140-149: Comparison superinstructions (10 opcodes)
150-191: Reserved for future superinstructions (42 opcodes)
```

### 2. Initial Superinstruction Set

#### OP_DEFINE_GLOBAL_CONST (100)
- Fuses: OP_DEFINE_GLOBAL + OP_CONSTANT
- Encoding: `[100] [global_idx:u8] [const_idx:u8]` (3 bytes)
- Replaces: `[OP_CONSTANT] [const_idx] [OP_DEFINE_GLOBAL] [global_idx]` (4 bytes)
- Savings: 1 byte per occurrence

#### OP_GET_GLOBAL_ADD (110)
- Fuses: OP_GET_GLOBAL + OP_ADD
- Encoding: `[110] [global_idx:u8]` (2 bytes)
- Replaces: `[OP_GET_GLOBAL] [global_idx] [OP_ADD]` (3 bytes)
- Savings: 1 byte per occurrence
- Note: Assumes second operand is already on stack

#### OP_GET_GLOBAL_GLOBAL (120)
- Fuses: OP_GET_GLOBAL + OP_GET_GLOBAL
- Encoding: `[120] [global1_idx:u8] [global2_idx:u8]` (3 bytes)
- Replaces: `[OP_GET_GLOBAL] [global1_idx] [OP_GET_GLOBAL] [global2_idx]` (4 bytes)
- Savings: 1 byte per occurrence

#### OP_GET_LOCAL_LOCAL (121)
- Fuses: OP_GET_LOCAL + OP_GET_LOCAL
- Encoding: `[121] [local1_idx:u8] [local2_idx:u8]` (3 bytes)
- Replaces: `[OP_GET_LOCAL] [local1_idx] [OP_GET_LOCAL] [local2_idx]` (4 bytes)
- Savings: 1 byte per occurrence

#### OP_CONSTANT_CONSTANT (130)
- Fuses: OP_CONSTANT + OP_CONSTANT
- Encoding: `[130] [const1_idx:u8] [const2_idx:u8]` (3 bytes)
- Replaces: `[OP_CONSTANT] [const1_idx] [OP_CONSTANT] [const2_idx]` (4 bytes)
- Savings: 1 byte per occurrence

### 3. Peephole Optimization Pass

The compiler implements a post-emission peephole pass that:
1. Scans the generated bytecode for fusible patterns
2. Replaces matched patterns with superinstructions
3. Adjusts jump offsets and line numbers
4. Updates the constant pool if needed

Implementation approach:
- Single backward pass after function compilation
- Pattern matching state machine
- Safe bytecode rewriting with offset tracking

### 4. VM Handlers

Each superinstruction has a dedicated VM handler that performs the fused operation:

```zig
// Pseudo-code for OP_DEFINE_GLOBAL_CONST handler
case OP_DEFINE_GLOBAL_CONST: {
    const global_idx = READ_BYTE();
    const const_idx = READ_BYTE();
    const name = READ_CONSTANT(global_idx);  // Global name from const pool
    const value = READ_CONSTANT(const_idx);   // Value from const pool
    table_set(&vm.globals, name.as.string, value);
    DISPATCH();
}

// Pseudo-code for OP_GET_GLOBAL_ADD handler
case OP_GET_GLOBAL_ADD: {
    const global_idx = READ_BYTE();
    const name = READ_CONSTANT(global_idx);
    Value value;
    if (!table_get(&vm.globals, name.as.string, &value)) {
        runtimeError("Undefined variable");
        return INTERPRET_RUNTIME_ERROR;
    }
    const b = pop();
    const a = value;
    push(add(a, b));  // Add operation
    DISPATCH();
}
```

### ⚠️ Issues Discovered

#### Pattern Matching Accuracy Problem
The initial pattern matching implementation has a fundamental flaw:

**Problem**: The DEFINE_GLOBAL + CONSTANT pattern was incorrectly specified.
- **Assumed pattern**: `[OP_CONSTANT value_idx] [OP_DEFINE_GLOBAL name_idx]`
- **Reality**: DEFINE_GLOBAL already expects the variable name as a constant index, with the value on the stack

**Impact**: The peephole optimizer was incorrectly fusing patterns, causing runtime errors ("Invalid constant index").

**Root cause**: Pattern analysis was based on opcode frequency pairs without fully understanding the semantic relationship between instructions.

#### Current Status
The peephole optimizer is **temporarily disabled** in `compiler.zig` to prevent bytecode corruption.
